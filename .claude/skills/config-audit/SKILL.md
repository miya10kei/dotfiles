# Config Audit

見落としを防ぐため、対象を全部列挙してから読み、主張は確かめてから報告する。直すのはユーザーが選んだものだけ。

## 1. 対象を列挙して既読を管理する

- `git ls-files` から一覧を作り、ファイルごとに「読んだ / 読んでいない」を付ける。最後に読んでいないファイルを報告に必ず書く
- lintやshellcheckが通ったことは「読んだ」に含めない
- 依頼が範囲を絞っていればそれに従う。絞っていなければ、`config/nvim/` のような大きな塊も含めて全部を対象にする

## 2. 観点

- 既定値と同じ設定（例: `push.default=simple`、`color.ui=auto`）
- 効いていない設定
    - 定義のないドライバやプラグインを参照している（例: `.gitattributes` の `diff=json`）
    - gitに無視されるalias（組み込みコマンドと同名）、同名の関数を指すだけのalias
    - パターンの書き間違い（例: `.editorconfig` の `{md, markdown}` の空白）
    - コメントアウトされたまま残っている設定
- 古い書き方・置き換えられる仕組み（ツール本体が出力するようになった統合スクリプト、廃止されたオプション、自前のページ送りなど）
- 使っていないツール・プラグイン・PATH・FPATH・.gitignoreの行
- 削除済みのものへの参照の残り（`grep -rn` でリポジトリ全体を探す）
- 壊れる・危ない定義（例: `env` を `env | sort` にするalias、jqの `==` と `=` の取り違え）
- `CLAUDE.md` のルールに反するもの（OS・アーキの分岐、POSIXの範囲外のオプション、パッケージの公開日制限）

## 3. 報告する前に確かめる

- 挙動についての主張は実際に動かして確かめる。確かめられないものは推測と書く
    - 外部コマンド（`aws`・`fzf`・`mise where` など）はPATHの先頭に置いたスタブで置き換えて実行する
    - 設定を変えると何が変わるかは、オンとオフで比べる（例: `mise latest` を `MISE_MINIMUM_RELEASE_AGE` ありとなしで実行する）
    - 書き換え案は、変更前と変更後の出力を同じ入力で比べる（特殊文字・空・長い値を含める）
- 動かない原因をツールの制約と決めつける前に、テスト環境の不備を疑う
- 確認方法の詳細は `CLAUDE.md` の「検証」に従う

## 4. 直す前にユーザーに選んでもらう

- 見つけたものをAskUserQuestionで提示する。ラベルは「削除する」「置き換える」など実行する操作にし、説明には根拠と、選んだ場合の不利益を書く
- 選ばれたものだけを直す。分野ごとにコミットを分ける

## 5. 報告

次の4つを分けて書く。

- 直したこと
- 確かめたこと・確かめていないこと（読んでいないファイルを含む）
- 挙動の変化
- ユーザーがすること（`git pull` 後の再起動、不要になったツールのアンインストールなど）
