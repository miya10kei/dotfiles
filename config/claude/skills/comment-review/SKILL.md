# Comment Review

自分が書いたコメントを監査し、**不要なものを削って必要なものだけ残す**。
「指摘されたら削る」のではなく、実装直後に自分で機械的に通す。

## 原則

コメントは **コードが答えられない問いにだけ答える**。

| 誰が語るか | 内容 |
| --- | --- |
| コード | What（何をしているか）/ How（どうやっているか） |
| コメント | **Why**（なぜこうしたか）/ **Why not**（なぜ別解を採らなかったか）/ 制約・罠 |
| コミットメッセージ・PR | 変更の経緯、実測ログ、調査の過程 |
| ADR・debt・仕様書 | 設計判断そのもの、恒久的なルール |

コメントで説明したくなったら、まず **リネーム・関数抽出・型の導入で消せないか** を考える。
コードで表現できるものをコメントで補うのは、負債を 2 箇所に増やす行為。

## 対象

**今回の差分で追加・変更したコメントのみ**。既存コメントの大掃除は別タスクとして切る
（差分が読めなくなり、レビューコストが跳ね上がるため）。

**コメント記号を持たない説明も同じ基準で見る** — Terraform の `description`、OpenAPI /
`@Schema` の description、変数・設定の説明文。grep では拾えないので、変更したファイルを
直接読んで確認する。ここが実質の主戦場になることがある。

## ワークフロー

### Step 1: 差分のコメントを抽出

```bash
# 自分のコミット範囲・自分が触ったパスに絞る
git diff -U0 <前回レビュー時点>..HEAD -- <自分が変更したパス> | grep -nE '^\+\s*(//|#|\*|/\*|<!--)'
```

KDoc / JSDoc / docstring / プロパティファイルの `#` コメントも対象。

**`<base>...HEAD`（三点）を素で使わないこと。** 作業中に main / develop の取り込みマージが
入ると、**他人のコメントが大量に混ざる**（実例: 他チームの新規ファイル 40 行超が抽出され、
選別に時間を取られた）。範囲とパスの両方で絞り、混ざったものは監査対象外として報告に明記する。

### Step 2: 1 件ずつ分類する

各コメントに対して以下の 5 問を順に当てる。**最初に該当した行動を採る**。

1. **リネーム・関数抽出で置き換えられるか？** → コメントを消して**コードを直す**
2. **コードを読めば分かるか？**（言い換え・シグネチャの再掲・自明な前置き） → **削除**
3. **同じことが他所に書かれていないか？**（同ファイルの description / 呼び出し側と定義側 /
   ADR・debt・仕様書） → **一箇所に集約**し、他は消す
4. **置き場所が違うか？**（経緯・実測値・調査メモ・一般論の規約） → コミット / PR / ADR / rules へ**移す**
5. **消したとき、次に触る人が壊す変更をしうるか？** → **残す**（必要なら 1〜2 行に圧縮）

問 3 は見落としやすい。**定義側（モジュールの description・KDoc）と呼び出し側（設定値の横の
コメント）に同じ説明を二重に書く**のが典型で、片方を直したときにもう片方が嘘になる。
呼び出し側に残すのは「その呼び出しでしか決まらないこと」（渡した値の根拠など）だけにする。

### Step 3: まとめて 1 pass で修正

個別の後追い修正にしない。削除・圧縮・移動を一度に適用する。

### Step 4: 再検証

コメント行の削除で lint / formatter（行長・KDoc 必須ルール等）が落ちうる。
該当モジュールの lint とテストを実行して green を確認する。

### Step 5: 報告

削った件数を**分類ごとに**、残した判断は**理由つきで**報告する。
「情報を捨てた」のではなく「置き場所を移した」ことが伝わるように書く。

## 削る（典型パターン）

- **コードの言い換え** — `// ユーザーを取得する` の直下に `fetchUser()`
- **シグネチャの再掲** — 型・引数名・戻り値をなぞるだけの KDoc
- **自明な前置き** — クラス名から明らかな役割説明、「〜のためのクラス」
- **作業経緯・実測ログ・日付入りの調査メモ** — commit / PR に属する
- **過去の選択肢との対比** — 「~~A~~ ではなく B」「A を挟まず B」「A から変更」。
  現在の状態だけを書く。**なぜ B なのかの根拠は残してよいが、A を経由しなかったことは経緯**
- **コメントアウトされたコード** — git が覚えている。消す
- **一般論の注意書き** — 「〜すること」はリポジトリの rules / lint に属する
- **変更履歴・TODO の墓場** — Changelog は git、TODO は issue へ
- **装飾的な区切り線の乱発** — セクションが 1 個しかないのに区切る等

## 残す（コードから導出できない事実）

- **非自明な選択の Why / 却下した代替案** — 「A ではなく B にした理由」
- **外部仕様・ツールの癖による制約** — build-time / runtime の違い、API のリトライ条件、
  ライブラリの既知バグ
- **触ると壊れる罠** — 「ここに X を書くと Y が無効化される」
- **不変条件・前提** — 呼び出し順序、単位、スレッド安全性、null の意味
- **参照** — ADR 番号、issue URL、仕様書リンク
- **非自明なアルゴリズムの意図** — 計算量、境界条件の根拠

## 陳腐化させない書き方

- 具体的な**ファイルパス・行番号・件数・日付**を書かない（差分ですぐ嘘になる）
- **実測結果の表**を書かない。「実測でこうだった」は PR 本文へ。コメントには結論だけ残す
- 参照は**壊れにくい単位**で書く（ADR 番号・プロパティ名・クラス名 > パス）

## 判断を誤らないための注意

- **コメントゼロが正義ではない。** Why を失う削りすぎも同じ失敗。判定は Step 2 の 5 問で行い、
  「短いほど良い」で削らない
- **密度はリポジトリに合わせる。** 周囲より自分の差分だけ饒舌なら、それが過剰のサイン
- **削る前に移す。** 価値ある情報を含むコメントは、消す前に commit message / PR 本文へ移送する
- 差分が大きい場合は Agent tool でサブエージェントに分担させ、メインコンテキストを汚さない
