# save-meeting-minutes

会議の生の議事録（自動生成のサマリーと文字起こし）を、後から読み返せる議事録ノートに再構成してObsidianのvaultに保存するスキル。

このスキルが持つのは**手順**だけで、**フォーマットと固有名詞はvault側に置く**。フォーマットはvaultのテンプレート、人名は人物ノート、社内用語は用語集ノートから毎回読む。スキル本体に会社や個人に固有の内容を書き足さないこと（このスキルは公開リポジトリで管理される）。

---

## 知っておくべきこと

手順の理由になっている事実。読み飛ばさないこと。

1. **自動生成のサマリーは、もっともらしく間違う。** 担当者の取り違え（依頼した人を実施者にする）、途中で覆った案を最終決定として書く、発言に無い語（「連続」「必ず」など）を補う、といった誤りが実際に起きる。サマリーを整形するだけでは誤りを清書することになるので、文字起こし全文との突合を省かない。
2. **文字起こしは人名と固有名詞を高頻度で誤認識する。** 姓が1〜2文字欠ける、社内用語が意味のない音の並びになる、といった形で出る。人物ノートの読みと用語集が、正しい表記に当てる手がかりになる。
3. **聞き取れない箇所を推測で埋めない。** 解釈が割れる箇所は本文に暫定の解釈を書き、「要確認」に文字起こしの前後を引用して残す。ユーザーは会議の当事者なので、原文を見れば数秒で確定できる。
4. **議事録は「その場で決まったこと」の記録。** 後から確定した内容を混ぜるときは、そうと分かる注記を付ける。経緯を追うときに区別できなくなるため。

## 前提とするvault構成

```
Templates/meeting_note.md      議事録のテンプレート（フォーマットと記入ルールの正本）
Templates/person.md            人物ノートのテンプレート
Meetings/Meetings.md           全会議の横断一覧と未完了アクション
Meetings/<シリーズ名>.md        シリーズ索引（開催回の一覧と継続論点）
Meetings/<シリーズ名>/YYYY-MM-DD_<シリーズ名>.md   各回の議事録
Meetings/用語集.md             誤認識されやすい社内用語と正しい表記
People/<フルネーム>.md          人物ノート（frontmatterに reading と roles）
People/People.md               人物ノートの一覧
```

- 一覧はBases、アクションアイテムの集計はDataviewを使う。
- vaultの操作はObsidianのMCPで行う。vaultが複数ある場合は、どのvaultに記録するかをユーザーの指示や設定から判断し、判別できなければ尋ねる。
- 上記のファイルが無い場合は「初回セットアップ」を参照。

---

## 全体の流れ

1. 素材を揃える（議事録ファイル、予定の情報、資料のリンク）
2. vaultの文脈を読む（テンプレート、人物ノート、用語集、シリーズ索引）
3. テンプレートに沿って下書きする
4. サブエージェントで文字起こし全文と突合する
5. ノートを保存する
6. シリーズ索引・人物ノート・用語集を更新する
7. 結果と要確認を報告し、ユーザーの回答で確定させる

---

## Step 1. 素材を揃える

**議事録ファイル**
- ユーザーがファイルを指定していればそれを使う。
- 無ければ `fetch-meeting-minutes` スキルで取得する。このファイルは整形のための中間素材なので、保存先には一時ディレクトリを提案する。vaultやリポジトリの中には置かない。

**予定の情報**（Googleカレンダーの予定に紐づく会議の場合）

```bash
gws calendar events get --params '{"calendarId":"primary","eventId":"<EVENT_ID>"}' \
  | jq '{summary, start: .start.dateTime, end: .end.dateTime, htmlLink, attendees: [.attendees[]?.displayName]}'
```

- `EVENT_ID` は、fetch-meeting-minutes で予定を検索済みならその結果を使う。ファイルを直接渡された場合は、日付の範囲で `gws calendar events list` を実行し、タイトルで絞って特定する。見つからなければ、日時とURLをユーザーに尋ねる。
- 「〇〇関連の会議」「先月の会議すべて」のように範囲で頼まれたときは、`q` 検索に頼らない。`q` は日本語や記号を含むタイトルを取りこぼすことがある。期間内の全予定を取得し（`nextPageToken` で最後まで）、タイトルと、議事録の添付の有無で絞る。
- 「記録できていない会議」のように未記録分を頼まれたときは、期間内の予定とvaultの既存ノートを、日付と会議名で突き合わせて差分を出す。`Meetings/` 配下だけでなく、1on1や面接など別形式の記録の置き場所も見る。
- 範囲で頼まれたときに対象にするのは、ユーザー本人が参加した会議だけ。参加の有無は出欠の回答だけで決めず、文字起こしの発言者にユーザーがいるかで確かめる（承諾したまま欠席した会議、辞退したが出た会議があるため）。参加していない会議は尋ねずに外し、外した会議は報告に一覧で添える。ユーザーが会議を名指しした場合はこの限りでない。
- 1つの予定に議事録が複数付いている場合は、文字起こしの中身がある方を使う。開始直後に文字起こしが終了している空のメモが混ざることがある。
- 予定に付いた添付を、その回の資料と決めつけない。繰り返しの予定には過去の回の添付が残り続ける。日付と中身を見て、その回のものかを確かめる。
- `start` `end` から開催日と時刻、`htmlLink` から予定のURLを取る。
- 記録する時刻は予定の時刻でよい。実際の終了が大きくずれていても合わせる必要はない。

**資料のリンク**
- アジェンダ、要件書、チケット一覧など、会議で使った資料があるかをユーザーに尋ねる。議事録ファイル内にリンクがあればそれも拾う。
- 資料の中身を読める場合は読む。Step 3で「資料に書いてあることを議事録に写さない」ために必要になる。
- リンクのタイトルは推測せず、ページから取得する。追跡用のクエリパラメータは外す。

## Step 2. vaultの文脈を読む

下書きの前に次を読む。どれも下書きの質を直接左右する。

| 読むもの | 使いみち |
|---|---|
| `Templates/meeting_note.md` | セクション構成、frontmatter、冒頭の「記入ルール」。**ここに書かれたルールがこのスキルの記述より優先する** |
| `People/` の各ノートのfrontmatter | 出席者と担当者をリンクにする対象。`reading`（読み）は誤認識された人名を当てる手がかり、`roles` は発言の立場を理解する手がかり |
| `Meetings/用語集.md` | 文字起こしで崩れた社内用語を正しい表記に戻す |
| `Meetings/<シリーズ名>.md` | 前回までの継続論点。今回の会議で決着したものがあるかを見る |
| 同じシリーズの直近の議事録 | 書きぶりと粒度を揃える |

テンプレートの記入ルールは、運用しながらユーザーが書き換えていく。スキル側に同じルールを書き写すと古くなるので、毎回テンプレートから読む。

---

## Step 3. 下書きする

テンプレートのセクション構成と記入ルールに従って下書きを作る。ルールの文言だけでは伝わりにくい、判断の勘所を挙げる。

**結論を先に、経緯を後に**
- 決定事項・継続論点・アクションアイテムだけを読めば、何が決まり何が残ったかが分かるようにする。
- 議題別メモには、結論の言い換えではなく、経緯・根拠となる数値・却下した案とその理由を書く。「なぜそう決めたか」は後から最も参照される。
- 同じ内容を複数のセクションに書かない。

**サマリーの細切れを議題に束ね直す**
- 自動生成のサマリーは、同じ議題を発言順に何項目にも分けて並べる。議題ごとに1つの見出しへ統合する。

**資料と二重管理にしない**
- 資料（要件書など）に書いてある内容は写さず、リンクに任せる。議事録に残すのは、会議で出た補足・指摘・資料と食い違う点・決定。
- 資料は更新されるので、写した内容は古くなる。
- 資料を読めなかった場合や、会議の内容が資料に載っていなかった場合は、内容を議事録に残し、その理由を1行添える。

**その会議から作られたノートが既にある場合**
- 会議の文字起こしを基に作ったまとめ（振り返りの成果物など）がvaultにあれば、資料としてリンクし、そこにある内容は写さない。議事録には、そのノートに無い補足と、発言者ごとの立場を残す。
- そのノートと文字起こしが食い違う箇所は、「要確認」に一覧で書く。既存のノートは勝手に直さず、直すかどうかはユーザーに委ねる。

**人と用語**
- `attendees` とアクションアイテムの担当者は、人物ノートがあればリンクにする。本文中の名前はリンクにしない。
- 人物ノートが無い人は、推測でフルネームを補わない。
- 用語集と人物ノートの読みで直せない固有名詞は、文字起こしの表記のまま書き、Step 7で確認する。

**アクションアイテム**
- 「やること」だけを1行で書く。期日は会議で決まったものだけ付ける。
- 会議中に済んだこと（その場で画面共有して説明した、など）はアクションにしない。サマリーは発言をそのままタスク化しがちなので注意する。

**要確認**
- 解釈が割れる箇所は、本文でどう扱ったか、文字起こしの原文（前後の発言を含む）、そう解釈した理由、の3点を書く。

---

## Step 4. 文字起こし全文と突合する

下書きができたら、**下書きを書いた自分とは別のサブエージェント**に、文字起こし全文と下書きを突き合わせさせる。自分で見直すだけでは、サマリーを信じた前提のまま読んでしまい、誤りに気づきにくい。

サブエージェントには次を渡す。

- 議事録ファイルのパス（全文を最後まで読むこと、編集はせず指摘だけ返すこと）
- 下書きの本文
- 人物ノートの氏名・読みと、用語集（誤認識を読み解くため）
- ノートの方針（文字起こし本文は入れない、雑談は落とす、資料の内容は写さない）。これらは指摘対象外と伝える
- 見てほしい観点
  - **欠落**: 文字起こしにあって下書きに無い、後から参照する価値のある情報（決定、数値、理由、懸念、担当、期日、却下した案とその理由）。サマリーにも無いものを特に重視する
  - **誤り**: 下書きが文字起こしと食い違う箇所（数値、担当者、決定内容、因果関係）。サマリー由来の誤りも含む
  - **重複**: 同じ内容が複数のセクションに実質そのまま出ている箇所
  - **冗長**: 削れる語句
- 報告の形式: 指摘ごとに、下書きの該当箇所、根拠となる行番号と発言の短い引用、修正案。文字起こしから確実に読める事実と、誤認識を補った推測を区別させる

戻ってきた指摘は、採用する前に根拠の行を自分で読んで確かめる。サブエージェントの報告も間違うことがある。確かめた結果を下書きに反映し、推測の域を出ないものは「要確認」に回す。

報告が長いと途中で切れて届くことがある。全文をファイルに保存させ、ファイルから読む。

### 長い会議や複数件をまとめて処理するとき

文字起こしが数千行ある会議や、複数の会議を一度に頼まれた場合は、下書きもサブエージェントに任せてよい。その場合も、下書きと突合は別々のサブエージェントに担当させる。同じエージェントに両方やらせると、自分の下書きを正しい前提で読んでしまう。

- 下書き担当には、Step 2 で読むべきもの（テンプレート、人物の氏名・読み・ロール、用語集、同じシリーズの完成済みノート）と、確定している情報（日付、時刻、URL、保存先）を渡す。下書きはvaultではなく一時ディレクトリに書かせる。
- 件数が多いときは、着手前に対象の一覧と処理量の目安をユーザーに示し、範囲を確認する。1on1や面接のように性質の違う会議が混ざっていないかも見る。
- vaultに会議以外の記録形式（1on1、面接など）が既にあれば、その種類の会議はそちらの置き場所と形式に合わせる。
- 要確認は会議ごとに聞かず、全件を保存した後にまとめて示す。同じ人名や用語の確認が何度も出るのを避けられる。

## Step 5. 保存する

- パス: `Meetings/<シリーズ名>/YYYY-MM-DD_<シリーズ名>.md`
  - ファイル名を日付だけにしない。デイリーノートと同名になり、リンク先が曖昧になる。
- `created_at` は実際に書き込む時刻を `date '+%Y-%m-%d %H:%M:%S'` で取得して入れる。推測の時刻を書かない。
- 単発の会議でシリーズが無い場合は、vaultに単発用の置き場所があればそこに置く。無ければ、置き場所と `series` の扱いをユーザーに確認する。
- 同じ日付のノートが既にあれば上書きせず、ユーザーに確認する。

---

## Step 6. 索引・人物ノート・用語集を更新する

**シリーズ索引（`Meetings/<シリーズ名>.md`）**
- 無ければ `assets/series_index.md` を元に作る。
- 今回の継続論点を、該当する見出しへのリンク付きで追記する（`[[<ノート名>#<見出し>|<表示名>]]`）。
- 前回までの継続論点のうち今回決着したものは、索引から外す。

**横断一覧（`Meetings/Meetings.md`）**
- BasesとDataviewで自動的に更新されるので、手で編集しない。

**人物ノート**
- 出席者や担当者に人物ノートが無い人がいたら、作るかどうかをユーザーに尋ねる。作る場合は読みとロールも聞く。推測で埋めない。
- `Templates/person.md` に従う。

**用語集（`Meetings/用語集.md`）**
- 今回、誤認識から正しい表記を確定できた用語があれば追記する。次回以降の整形で同じ確認を繰り返さずに済む。

---

## Step 7. 報告し、要確認を確定させる

保存後、次を簡潔に報告する。

- 保存したノートのパス
- サマリーから直した誤り（何をどう直したか）
- 要確認の一覧
- 文字起こし由来で未確認の人名・固有名詞

ユーザーが回答したら、その都度ノートを更新する。

- 確定した項目は「要確認」から削除する。空になったらセクションごと削除する。
- 会議の場では決まっておらず、後から確定した内容は「（会議後に確定）」と注記する。
- アクションアイテムが完了したと分かったら、チェックを付け、結果は子の箇条書きで添える。
- 回答によって用語や人名が確定したら、用語集と人物ノートにも反映する。

---

## 初回セットアップ

vaultに前提のファイルが無い場合は、`assets/` の雛形を元に作成する。作成前に、既存のテンプレートやフォルダの命名規則を確認し、vault側の流儀に合わせる（frontmatterのキー名、カテゴリの付け方など）。

| 雛形 | 作成先 |
|---|---|
| `assets/meeting_note.md` | `Templates/meeting_note.md` |
| `assets/person.md` | `Templates/person.md` |
| `assets/meetings_index.md` | `Meetings/Meetings.md` |
| `assets/series_index.md` | `Meetings/<シリーズ名>.md` |
| `assets/people_index.md` | `People/People.md` |
| `assets/glossary.md` | `Meetings/用語集.md` |

雛形は出発点にすぎない。vaultに作成した後はvault側が正本になり、以降はそちらを読む。

## エラーハンドリング

| 症状 | 対応 |
|------|------|
| 議事録ファイルに文字起こしが無い（サマリーのみ） | 突合ができないことをユーザーに伝え、サマリーだけで作るか確認する。作る場合は、未検証であることをノートの要確認に明記する |
| テンプレートが無い | 「初回セットアップ」に従って作成するかを確認する |
| Dataview / Bases が使えない | ノートの保存は進め、一覧や集計が表示されない旨を報告する |
| 文字起こしが長く一度に読めない | 分割して最後まで読む。途中までで突合を終えない |
